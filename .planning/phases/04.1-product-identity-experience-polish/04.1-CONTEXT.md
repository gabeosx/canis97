# Phase 04.1: Product Identity & Experience Polish - Context

**Gathered:** 2026-08-27 (assumptions mode)
**Status:** Ready for planning

<domain>
## Phase Boundary

Give the existing native player one independent, release-quality product identity before public distribution: a new provider-neutral name and bundle identity, an original current-macOS app icon, consistently renamed product copy and presentation, richer but still bounded visual customization, and complete offline visual/accessibility validation of the authentication, compact-player, library, and appearance-management surfaces.

This phase does not change authentication, catalog, playback, metadata, local-library, or skin-safety behavior; add song favorites or playlist-service connections (Phase 04.2); add compatibility support bundles or client documentation; sign, notarize, publish, or install public releases (Phase 05); establish an App Store distribution channel; or decide whether service access is legally authorized.

</domain>

<decisions>
## Implementation Decisions

### Independent product name and affiliation boundary

- **D-01:** Replace **Sirius Mac** with one independent product name and matching product-owned identity before release. The final name must not contain “Sirius,” “XM,” “SiriusXM,” or otherwise imply that the app is an official Sirius XM Radio LLC product.
- **D-02:** Carry the chosen identity consistently through user-visible window and menu titles, accessibility labels, authentication and library copy, About/presentation text, app target/product/executable names, bundle identifiers, UTTypes, application-support and frame-restoration namespaces, build/launch scripts, test identities, and Phase 05 release inputs. Preserve safe migration from existing non-secret local library, appearance, and window-state locations where a rename would otherwise strand user data. The reusable `SiriusXMClient` library keeps its factual provider-facing name and boundary.
- **D-03:** Use “SiriusXM” only where it is factually necessary to identify the subscriber service or account, with the independent app name visually dominant. Include clear non-affiliation language in sign-in/onboarding, About, project/release presentation, and other contexts where a reasonable user could mistake affiliation. Exact wording remains subject to pre-release review; a disclaimer is not treated as permission to use provider marks or access the service.
- **D-04:** Before committing material public brand investment, screen the candidate name for exact and confusingly similar federal marks, spelling and phonetic variants, related software/media goods and services, common-law use, app listings, repositories, domains, business registries, and relevant icon design codes. Preserve a dated clearance record and treat attorney review before public launch or registration as a release-readiness item, not as a conclusion this phase can manufacture.

### Icon and visual identity

- **D-05:** Use an original, provider-neutral 2000s music-player visual language that complements the compact player without copying SiriusXM marks, official logos, dog imagery, channel artwork, Apple hardware, standard controls, or another player’s trade dress. Prefer a simple abstract music-device, signal/visualizer, or name-derived mark that remains recognizable at small sizes and does not depend on text.
- **D-06:** Use one Xcode 26 Icon Composer `.icon` file as the authoritative app-icon pipeline. Build it from a 1024×1024 layered square composition, leave system masking and Liquid Glass effects to Icon Composer, preserve one recognizable core across supported appearances, and configure the app target to use that file rather than maintaining an ambiguous second authoritative `AppIcon` catalog.
- **D-07:** Identity polish applies coherently to the native fallback, both bundled appearances, authentication, compact player, library, settings/appearance management, and release-facing presentation. It may refine names, colors, typography, bounded decorations, empty/error states, and supporting copy, but it must preserve truthful semantic state and native macOS interaction patterns.

### Bounded customization

- **D-08:** “Richer bounded customization” extends only the existing closed, declarative appearance path: app-owned visual tokens, finite semantic surface treatments, and noninteractive local decoration. It must not create a second renderer, executable behavior, remote content, arbitrary layout scripting, or authority over networking, authentication, playback, persistence, menus, window policy, or accessibility.
- **D-09:** Preserve the fixed 400×288 compact-player content size, native control geometry and semantics, minimum hit targets, keyboard focus order, VoiceOver labels and values, Reduce Motion behavior, readable focus/state indicators, and package-independent Native recovery. Existing `.siriusskin` packages must remain safely validated; schema changes require explicit versioning and compatibility handling rather than silently broadening authority.

### Visual and accessibility validation

- **D-10:** Add offline automated coverage for stale product-name and identifier references, icon target configuration, bounded skin authority, migration of non-secret renamed storage, and structural accessibility contracts. Provider credentials, WebKit sessions, Keychain state, live media, and SiriusXM requests are not needed for identity validation.
- **D-11:** Complete a deliberate visual/accessibility review across authentication states, populated and empty compact-player states, library collections and errors, appearance management, Native, Signal Glow, Tape Deck, and any revised bundled appearance. Validate light/dark or rendered icon appearances, Finder/Dock/Spotlight/About presentation, contrast, keyboard-only operation, VoiceOver labels/order/announcements, focus visibility, hit targets, and Reduce Motion.
- **D-12:** Repository launch safety remains binding. Planning may use static/offline tests and `xcodebuild build-for-testing`; it must not run the app, app-hosted tests, `xcodebuild test`, UI automation, or live SiriusXM activity until the user separately authorizes the required safety review and that review establishes a safe environment.

### Agent's Discretion

- Choose the exact independent product name after applying D-01 through D-04, and choose the exact icon concept between an abstract music-device/signal mark and a name-derived mark.
- Choose the exact non-affiliation wording, typography, palette refinements, bundled-appearance names, empty/error-state copy, and finite new visual tokens, provided the identity and accessibility boundaries above remain intact.
- Choose internal migration type names and one-way compatibility mechanics for non-secret preferences and managed appearance storage. Do not migrate, rename, expose, or weaken the provider-facing Keychain/session contract merely for cosmetic consistency.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `SkinAppearanceCatalog`, `ValidatedSkinAppearance`, and the shared compact renderer already provide one safe path for Native, bundled, and imported visual identity.
- Signal Glow and Tape Deck supply two distinct retro palettes that can seed a cohesive broader identity without adding another theme engine.
- `UITestHarness`, accessibility contract tests, compact-presentation tests, and offline skin script tests provide credential-free validation seams.
- Existing storage facades accept injected Application Support roots, enabling deterministic migration tests for renamed non-secret data.

### Established Patterns

- User-facing state follows confirmed semantic models; visual polish cannot invent playback, metadata, authentication, or persistence outcomes.
- Native controls, menu commands, window policy, accessibility semantics, and recovery stay app-owned even when appearance changes.
- Secret-bearing provider state remains in the current Keychain/session boundaries; product renaming is not authorization to materialize or migrate secrets through new stores.
- Exact executable and bundle identity are part of launch safety, so target, scripts, UI tests, and runtime verification must change atomically.

### Integration Points

- Replace current product strings and accessibility labels throughout app presentation while retaining factual “SiriusXM subscriber account” references where needed.
- Configure the new product/executable/bundle/icon identity in `project.pbxproj`, then update test-host, module, launcher, log-subsystem, UTType, and release-script consumers coherently.
- Add safe one-way lookup or migration for existing non-secret library, appearance, and frame-restoration data under legacy Sirius Mac paths.
- Extend the existing closed appearance schema only if the chosen identity needs finite new visual roles; render every built-in and imported appearance through the same validator and renderer.
- Expand offline/static identity and accessibility coverage first; defer launched visual review until its explicit safety gate is satisfied.

</code_context>

<specifics>
## Specific Ideas

- The product should feel like an original 2000s desktop music player, not a reskinned provider client and not a copy of Winamp or another legacy player.
- A signal/visualizer, compact music-device, or name-derived monogram is preferred over provider imagery or text-heavy icon art.
- The independent product name should remain dominant whenever factual SiriusXM compatibility or sign-in language appears.
- Icon QA should include Xcode/Icon Composer preview plus the built product in Finder, Dock, Spotlight, and About once launched-app review is authorized.

</specifics>
