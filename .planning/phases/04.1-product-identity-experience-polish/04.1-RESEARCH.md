## Summary

The phase is an application-identity migration, not a provider-client rename. The current product has hardcoded app-facing names across the Xcode target, executable, bundle IDs, test host, scene IDs, window autosave keys, Application Support roots, launch scripts, user-facing strings, and app log subsystem. The safe boundary is to migrate only app-owned, non-secret locations once while retaining the old Keychain generic-password identity and the factual `SiriusXMClient` package/module/log identity. This prevents a cosmetic identity change from losing a subscriber’s local library or forcing secret material through an unaudited migration. [VERIFIED: SiriusMac/Security/KeychainCredentialStore.swift:5-9] “It never falls back to preferences, files, or an alternate secret store.”

Use one product-name decision checkpoint first, with a dated screening record that explicitly says “screening only; not legal clearance.” USPTO states that similarity includes sound, appearance, meaning, and commercial impression, and related goods/services are part of the likelihood-of-confusion analysis. Its comprehensive-search guidance includes federal and state records, common-law/internet use, domains, international databases, and attorney review. [CITED: https://www.uspto.gov/trademarks/search/likelihood-confusion] [CITED: https://www.uspto.gov/trademarks/search/comprehensive-clearance-search-similar-trademarks]

For the icon, make one original layered 1024×1024 source composition and make a single `.icon` file the target’s app icon. Apple documents Icon Composer as the single multilayer source from which Xcode renders sizes and appearances, says the target’s App Icon field must match the `.icon` filename without the extension, and says adding an Icon Composer file replaces an existing app-icon asset catalog. [CITED: https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer] The repository currently has no icon source and no `ASSETCATALOG_COMPILER_APPICON_NAME` setting in the target configuration. [VERIFIED: SiriusMac.xcodeproj/project.pbxproj:147-170] “Resources … `SignalGlow.json` … `TapeDeck.json`”; “`PRODUCT_BUNDLE_IDENTIFIER = com.siriusmac.player;`”.

**Primary recommendation:** make the name-screening checkpoint and the product-identity constants/migration seam the first tracer; then change target identity, icon wiring, presentation copy, and bounded visual tokens as one coordinated vertical slice, with launched-app review explicitly deferred behind D-12.

## Product-Name and Clearance Workflow

1. Write a short candidate brief: exact spelling, spoken form, intended product category (“native macOS music/radio player for subscribers”), prohibited provider terms/images, and the abstract icon concept. This is a product-input record, not a trademark application. [ASSUMED]
2. Generate a small candidate set, then reject any candidate containing or suggesting “Sirius,” “XM,” “SiriusXM,” official logos/dog imagery, or another party’s distinctive player branding. The repository decision is binding; SiriusXM’s terms identify “Sirius,” “SiriusXM,” “XM,” the dog logo, and SiriusXM logo as marks and state that site/service use grants no right or license to use them. [VERIFIED: 04.1-CONTEXT.md:15-17] [CITED: https://www.siriusxm.com/sxm-web-terms-of-use]
3. For each surviving candidate, record exact, spaced, hyphenated, plural, phonetic, and likely misspelling queries in the USPTO Trademark Search system; review active and pending marks for similar sound, appearance, meaning, or commercial impression and related software/media services. [CITED: https://www.uspto.gov/trademarks/search/federal-trademark-searching] [CITED: https://www.uspto.gov/trademarks/search/likelihood-confusion]
4. Screen common-law and discovery surfaces: multiple web searches, macOS/App Store-like listings, GitHub repositories, domains, business registries, state trademark sources, and relevant international sources. USPTO explicitly recommends federal, TMOG, state, domain, Madrid, WIPO, EUIPO/TMview, and internet checks as part of a comprehensive search. [CITED: https://www.uspto.gov/trademarks/search/comprehensive-clearance-search-similar-trademarks]
5. For the icon concept, identify its prominent elements, look up the relevant USPTO design codes, then retain the exact design-code and text queries/results in the same record. USPTO says design-code search covers design elements and does not provide reverse-image search. [CITED: https://www.uspto.gov/trademarks/search/design-search-codes]
6. Choose one candidate only after the recorded screen has no unresolved high-risk collisions. Record the selection, date, sources searched, query variants, result links/screenshots, and unresolved ambiguities; label it **“independent screening completed — not legal clearance.”** Request U.S.-licensed trademark-attorney review before public launch or registration. USPTO itself says an attorney can conduct and interpret a comprehensive clearance search. [CITED: https://www.uspto.gov/trademarks/search/comprehensive-clearance-search-similar-trademarks]

**Required planner checkpoint:** `checkpoint:human-verify` after the candidate record and before irreversible target/bundle/package naming. The final independent product name is a decision the phase may make; its legal availability is not established by this implementation work. [ASSUMED]

### Non-secret Migration Pattern

Use a one-way, idempotent, destination-first read/copy/verify/mark sequence per storage kind:

1. Compute the new app-owned root and the fixed legacy `Sirius Mac` root.
2. If a destination completion marker exists, never reimport legacy state.
3. Create/read the destination without deleting the legacy source.
4. Copy only declared safe fields or validated package/selection data.
5. Persist the destination atomically, verify the expected value can be read, then write the marker.
6. On any read/validation/write failure, use the existing safe default/in-memory fallback and leave the legacy source intact; no best-effort deletion.

This matches the library’s established behavior: [VERIFIED: SiriusMac/Library/LibraryStore.swift:528-549] “Migration is semantic and idempotent: opaque SQLite files are never moved, deleted, or adopted.” The selection store already rejects unknown keys and restores Native on malformed/unsupported records. [VERIFIED: SiriusMac/Skins/SkinSelectionStore.swift:125-147] “`Set(dictionary.keys) == ["schemaVersion", "identifier", "classification"]`” and “`(try? load()) ?? .native`”.

**Do not migrate Keychain.** The default Keychain service derives from the old bundle identifier, but the current contract says it has one generic-password identity, only safe error classifications, and no fallback. [VERIFIED: SiriusMac/Security/KeychainCredentialStore.swift:5-9] “single generic-password item identity” and “never falls back to preferences, files, or an alternate secret store.” [VERIFIED: SiriusMac/Security/KeychainCredentialStore.swift:53-63] “`service: String = Bundle.main.bundleIdentifier ?? "com.siriusmac.player"`”. Keep this compatibility fallback unchanged for this phase; an intentional secret rotation/migration requires separate security review, user consent, and its own recovery design. [ASSUMED]

### Icon Composer Pattern

1. Create one original 1024×1024 layered square source composition with a readable abstract device/signal/monogram core, no provider or third-party player imagery, and minimal/no text. Apple recommends an app icon that is unique and recognizable, vectored foreground art when practical, and clear foreground edges. [CITED: https://developer.apple.com/design/human-interface-guidelines/app-icons]
2. Build `<ChosenProductIcon>.icon` in Icon Composer, separating groups/layers that need default, dark, or mono variation. Apple says Icon Composer uses a single layered structure for appearance variants and that the system applies masking. [CITED: https://developer.apple.com/icon-composer/] [CITED: https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer]
3. Add the `.icon` as the sole app-icon source in the Xcode project and set the app target’s App Icon field to its basename. In project-file terms, verify the generated build configuration resolves `ASSETCATALOG_COMPILER_APPICON_NAME` to that basename; this exact build-setting key is an implementation expectation to verify with `xcodebuild -showBuildSettings`, not a source-of-truth fact established by the cited Apple page. [ASSUMED]
4. Remove/avoid a competing authoritative `AppIcon` asset catalog. Apple says a project Icon Composer file replaces an existing icon asset catalog; older OS fallback generation is automatic, but this project targets current macOS only. [CITED: https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer] [VERIFIED: AGENTS.md:17-17]
5. Keep the editable `.icon` and its imported layer sources in a clear app resource directory tracked by Xcode. Do not generate manually maintained multiple-size raster icon sets. [CITED: https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer]

### Bounded Appearance Extension Pattern

Extend `SkinManifest` only through explicit schema versions, fixed new optional/required keys, finite `CompactSkinSurface` roles, bounded primitive values, and projection from `ValidatedSkinAppearance`. Do not inspect imported free-form data in the view or add a `switch` renderer by skin name.

The closed path is already present: [VERIFIED: SiriusMac/Skins/SkinAppearance.swift:84-95] “`enum CompactSkinSurface`” contains “`canvas`”, “`metadata`”, “`status`”, “`transport`”, “`footer`”, “`interactiveAccent`”, and “`criticalState`”. [VERIFIED: SiriusMac/Skins/SkinAppearance.swift:220-230] “`keys.isSubset(of: requiredKeys.union(optionalKeys))`” and “`guard manifest.schemaVersion == 1`”. [VERIFIED: SiriusMac/Skins/SkinAppearance.swift:116-123] “If any requested decoration is unavailable at render time, the complete static Native value wins.”

For compatibility, accept schema 1 exactly as it is today. If a new appearance capability is needed, make schema 2 decoding/validation explicit, preserve v1 behavior, and test that v1 bundled/imported fixtures render the same projection. Unknown fields must remain rejected until a version-aware validator recognizes them. [ASSUMED]

## Common Pitfalls

### Pitfall 1: Choosing a name before screening it

**What goes wrong:** Target/product/module/bundle changes become costly to undo after a trademark collision. **Avoid:** make exact name and icon concept a blocker checkpoint before Xcode identity mutation; retain a dated record that is explicitly not clearance. [CITED: https://www.uspto.gov/trademarks/search/comprehensive-clearance-search-similar-trademarks]

### Pitfall 2: Treating the bundle-ID change as harmless

**What goes wrong:** Application Support, UserDefaults, window frame autosave, and default Keychain service names can fork state. **Avoid:** migrate only declared non-secret state; keep Keychain untouched. [VERIFIED: SiriusMac/Library/LibraryStore.swift:508-549] [VERIFIED: SiriusMac/Security/KeychainCredentialStore.swift:5-9]

### Pitfall 3: Renaming the provider library

**What goes wrong:** The repairable SiriusXM protocol boundary loses its factual semantics and creates an unnecessary public API refactor. **Avoid:** preserve the `SiriusXMClient` package/module and provider diagnostic category. [VERIFIED: SiriusMac.xcodeproj/project.pbxproj:181-190] [VERIFIED: Packages/SiriusXMClient/Sources/SiriusXMClient/Diagnostics/SafeDiagnosticEvent.swift:72-78]

### Pitfall 4: Adding a second appearance renderer for polish

**What goes wrong:** Native controls, fixed geometry, recovery, and accessibility diverge between themes. **Avoid:** add finite tokens only to the existing manifest/validator/catalog/renderer pipeline. [VERIFIED: SiriusMac/Skins/SkinAppearance.swift:84-95] [VERIFIED: SiriusMac/Skins/SkinAppearance.swift:287-351]

### Pitfall 5: Assuming the icon works because the source artwork looks correct

**What goes wrong:** The target points at the wrong icon source, default/dark/mono variants lose legibility, or a stale catalog remains authoritative. **Avoid:** assert target association/build setting and bundle inspection offline; defer Finder/Dock/Spotlight/About review until launch authorization. [CITED: https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer]

### Pitfall 6: Running the attractive visual-review lane too early

**What goes wrong:** UI tests or app launch violate the repository’s safety hold. **Avoid:** stop at static tests and `build-for-testing`; make visual/accessibility review a separately authorized final checkpoint. [VERIFIED: AGENTS.md:246-255]

## Recommended Task Ordering (Tracer-First and Reversible)

1. **Wave 0 — product-decision tracer (checkpoint):** establish a dated candidate/visual-concept screening record and select the single independent product name. No Xcode, bundle ID, asset, or persistent-state mutation before this gate. [CITED: https://www.uspto.gov/trademarks/search/comprehensive-clearance-search-similar-trademarks]
2. **Wave 1 — identity inventory and migration seam:** add product/legacy identity constants plus unit tests for legacy non-secret lookup, idempotence, failure preservation, and no Keychain migration. This is reversible because it only adds compatibility reading. [VERIFIED: SiriusMac/Library/LibraryStore.swift:528-549]
3. **Wave 2 — authoritative icon source:** create the original layered `.icon`, add it as the one target icon association, and add static/project checks. Artwork and target association can be independently adjusted before broader rename. [CITED: https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer]
4. **Wave 3 — atomic product identity cutover:** change target/product/executable/bundle/test identities, schemes, test host, scripts, app scene/log/UTType names, and source copy together. Verify new build product and static no-stale-reference allowlist. This is the highest-cost/most coupled operation. [VERIFIED: SiriusMac.xcodeproj/project.pbxproj:163-170]
5. **Wave 4 — visual polish through the closed seam:** evolve finite appearance tokens/schema only if needed, update Native/Signal Glow/Tape Deck and product surfaces coherently, and retain old schema compatibility. [VERIFIED: SiriusMac/Skins/SkinAppearance.swift:200-285]
6. **Wave 5 — offline evidence:** run source scans, isolated package tests, source-only script/launcher tests, and one `build-for-testing` lane with isolated DerivedData. Do not launch. [VERIFIED: AGENTS.md:246-255]
7. **Wave 6 — separately authorized manual review:** only after user safety authorization, review all listed states in Finder/Dock/Spotlight/About, keyboard/VoiceOver, contrast/focus/hit targets, and Reduce Motion. [VERIFIED: 04.1-CONTEXT.md:36-37]

**One-way/costly decisions:** final product name, bundle identifier, executable/app product name, module/target rename, distributed icon mark, persistent-root write namespace, and public release-facing strings. Do not freeze any of them before Wave 0; do not remove legacy non-secret roots until a later release-retention policy is authorized. [ASSUMED]
