## User Constraints (from CONTEXT.md)

### Locked Decisions

### Versioned expressive skin contract

- **D-01:** Introduce an explicit new schema version that supersedes the Phase 04/04.1 prohibition on skin-selected compact-player layout, geometry, and silhouette only within the bounded authority defined here. Schema versions 1 and 2 must continue to render unchanged or pass through an explicit deterministic migration before selection. Unsupported or invalid documents fail closed. — **Reversibility:** costly — once packages use the new public schema, undoing it requires package migration and compatibility handling.
- **D-02:** The expressive schema is a closed declarative vocabulary, not a general-purpose layout language. It may reference app-defined semantic slots, finite layout and silhouette variants, bounded layered decorations, typography tokens, and validated drag regions; it cannot contain code, scripts, constraints, selectors, arbitrary window flags, networking, remote URLs, or arbitrary file access.
- **D-03:** Every candidate must validate required semantic controls, frame bounds, non-overlap rules, minimum usable targets, text capacity, decoration budgets, asset references, and at least one usable drag region before it can render or become the durable selection. Invalid candidates leave the previous valid selection untouched.
- **D-04:** Bundled and imported themes use the same catalog, decoder, validator, semantic renderer, and recovery rules. The three bundled themes must prove the public contract rather than relying on privileged theme-specific renderers.

### Native behavior and accessibility sovereignty

- **D-05:** A skin arranges only a closed set of app-defined semantic controls and regions. Sirius owns the SwiftUI controls, action routing, enabled state, accessibility labels and values, keyboard behavior, focus order, VoiceOver announcements, playback truth, and recovery behavior. Skins cannot add, remove, rename, or redefine player actions. — **Reversibility:** costly — allowing packages to own semantics would couple public package data to behavior and require a coordinated schema and renderer migration to undo.
- **D-06:** Preserve the established 32×32 transport hit targets and readable app-owned focus/state indicators. Focus halos must remain visible inside the silhouette; decorative layers and drag overlays are hidden from accessibility; visual rearrangement must not destabilize semantic source order.
- **D-07:** Reduce Motion disables theme resize flourishes, bounce, parallax, and other nonessential movement. Theme changes may be instantaneous or use a restrained app-owned crossfade, and no theme may require animation to communicate state.

### Window shape, size, and restoration

- **D-08:** Expressive themes create an apparent nonrectangular silhouette inside a transparent rectangular `NSWindow`; Phase 04.2 does not promise arbitrary per-pixel click-through holes or a truly nonrectangular native event region. Retain a titled, key-capable window with narrow AppKit configuration instead of adopting a borderless window role.
- **D-09:** Compact-player sizes come from a small app-owned finite set selected by validated theme tokens. Native and legacy v1/v2 appearances remain 400×288. Imported skins cannot request arbitrary dimensions, minimums, maximums, or resize behavior.
- **D-10:** Theme-size changes are controller-owned and atomic: preserve the visible top-left position where possible, apply content minimum/maximum size together, choose the appropriate screen, clamp the complete frame into `NSScreen.visibleFrame`, persist a versioned compact position, and fall back to Native for invalid restoration state.
- **D-11:** Declarative drag regions are bounded, remain behind controls, cannot overlap interactive frames, and must leave all controls normally clickable. The application owns the actual drag gesture and window movement.

### Original bundled themes and asset provenance

- **D-12:** Ship three complete public themes named **Pixel Desk**, **Pocket Disc**, and **Aqua Vista**. Their shared inspiration is intentionally recognizable, but their names, artwork, icons, type treatment, layout details, and ornamentation must be original rather than copied from Apple, Sony, Microsoft, Winamp, or other products.
- **D-13:** Pixel Desk uses an original late-1990s desktop grammar: warm beige/gray surfaces, crisp pixel ornaments, bevels, dithering, and compact utility-window character. It must not reproduce Apple/Finder/Platinum assets, marks, system icons, or proprietary classic Mac fonts.
- **D-14:** Pocket Disc uses an original portable audio-device grammar: brushed or molded hardware surfaces, a segmented information display, asymmetric controls, labels, screws, and tactile details. It must not use Sony, MiniDisc, MD, Walkman, ATRAC, model-number, or product-copy assets or marks.
- **D-15:** Aqua Vista uses an original optimistic nature-and-technology grammar: sky, foliage, water, translucent glass, bubbles, highlights, and dimensional controls. It must not reproduce Microsoft/Windows marks, wallpapers, icons, or proprietary assets.
- **D-16:** Theme resources require explicit provenance. Typography uses system font tokens and, only if needed, a small reviewed set of app-bundled fonts with redistribution-compatible licenses such as OFL; imported packages cannot carry font binaries. Do not bundle Apple system font files, classic Mac fonts, Frutiger, or another commercial/vendor font without an independently verified license.

### Recovery and validation

- **D-17:** Native remains permanent, package-independent, non-removable, and reachable from an app-owned menu even if a selected skin cannot decode, validate, render, or fit on the active screens. Rendering failure restores Native and reports the recovery truthfully.
- **D-18:** Preserve archive, path, symlink, entry-count, byte, image-dimension, decode, and processing budgets from the existing importer. The expanded visual vocabulary must not broaden package access to secrets, URLs, executable behavior, menus, authentication, playback, persistence, or accessibility strings.
- **D-19:** Completion requires offline structural tests plus deliberate visual and accessibility review of Native, legacy v1/v2 packages, all three new themes, populated/empty/error player states, keyboard-only use, VoiceOver order and labels, focus visibility, contrast, target sizes, Reduce Motion, theme-size transitions, restoration, and failure recovery. App launch, app-hosted tests, and UI automation remain blocked until the repository's separate safety review authorizes them.

### Superseded upstream decisions

- **D-20:** Phase 04 `D-03` and Phase 04.1 `D-09` remain authoritative for Native and legacy packages but are superseded for validated new-schema themes where they require a universal 400×288 size or prohibit all app-defined layout authority. Phase 04 `D-01`, `D-02`, `D-12`–`D-16` and Phase 04.1 `D-08`–`D-11` remain authoritative wherever this context does not explicitly narrow or replace them.

### the agent's Discretion

- Choose the exact finite size values beyond legacy 400×288, schema field names, semantic-slot names, silhouette and layout variant names, asset-layer limits, and deterministic v1/v2 compatibility implementation within the locked bounds.
- Choose the original art direction details, surface materials, ornaments, safe public copy, reviewed font tokens or OFL font choices, shadows, and restrained transition treatment for each bundled theme.
- Choose the exact AppKit bridge mechanics for transparent content, titlebar treatment, traffic-light visibility, system shadows, shadow invalidation, screen selection, clamping, and frame migration while retaining normal key/main-window behavior and Native recovery.

### Deferred Ideas (OUT OF SCOPE)

- Local song favorites for later manual addition to a user's preferred music service — Phase 04.3.
- Spotify, Apple Music, or other external authentication, matching, playlist creation, and playlist-write APIs — outside Phase 04.3 and the current roadmap.
- Arbitrary per-pixel click-through window regions, skin-authored raw `NSWindow` flags, executable/scripted skins, networking, remote galleries or assets, arbitrary font binaries, and animated skin runtimes — outside Phase 04.2.
- Extending expressive themes to the library, authentication, settings, or other app windows — future phase unless separately scoped.
- Direct import of classic Winamp, macOS, MiniDisc, Windows, or other vendor skin/assets/formats — intentionally unsupported.

## Summary

Phase 4.2 is a schema-and-renderer evolution, not a theming overlay. Extend the existing exact-key decoder, package importer, `SkinAppearanceCatalog`, and render-time Native fallback with one schema-v3 appearance model. The model must compile untrusted package data into a validated, app-owned layout plan before any selection, persistence, SwiftUI rendering, or window resize occurs. Existing v1/v2 manifests retain their exact legacy appearance and `400 × 288` size. [VERIFIED: SiriusMac/Skins/SkinAppearance.swift:263-376; SiriusMac/Windows/CompactWindowController.swift:42-59]

The UI contract already fixes the finite public vocabulary: the layout variants are `legacyStack`, `desktopUtility`, `discConsole`, and `aquaPod`; the silhouette variants are `nativeRect`, `pixelNotched`, `discPod`, and `bubbleCapsule`; and the semantic slots are `artwork`, `channelIdentity`, `metadata`, `favorite`, `status`, `transport`, `library`, and `overflowMenu`. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:84-99] Build an app-created control registry/layout host around those exact slots, retaining the current typed `CompactPlayerAction` boundary and app-owned accessibility order. [VERIFIED: SiriusMac/Player/CompactPlayerPresentation.swift:210-221; SiriusMac/Player/CompactPlayerView.swift:77-281]

The highest-risk work is validator completeness and window transition correctness. Treat v3 layouts as hostile input: reject before promotion/selection if a slot is absent, duplicate, out of bounds, overlaps an interactive peer, violates the 32-point target floor, lacks text/focus clearance, references an unvalidated local asset, or lacks a valid drag rectangle. The trusted controller then atomically applies a finite size token and bounded transparent-window presentation, using an app-owned drag overlay behind controls. Apple’s documented `WindowDragGesture` is specifically intended to extend a hidden/transparent toolbar drag region; use it with window activation events. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:101-120] [CITED: https://developer.apple.com/documentation/swiftui/windowdraggesture]

**Primary recommendation:** Implement schema-v3 as a single strict compiler from manifest to `ValidatedSkinAppearance`/validated layout plan; preserve legacy rendering and drive all themed rendering plus bounded window transitions through that one output.

### Pattern 1: Validate to an app-owned layout plan, then render

**What:** Parse raw manifest values only to build a non-optional `ValidatedSkinAppearance` that contains finite layout/silhouette/type tokens, resolved URLs, and fully checked rectangles. The view must not inspect raw JSON or derive safety decisions at render time. This extends the existing `SkinManifestValidator` → `ValidatedSkinAppearance` pattern. [VERIFIED: SiriusMac/Skins/SkinAppearance.swift:263-451]

**When to use:** For every bundled, imported, restored, and migrated appearance. Bundled resources must not receive a privileged renderer. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-CONTEXT.md:20-23]

**Implementation guidance:** Keep a top-level `JSONSerialization` key-set check before `JSONDecoder`, as v1/v2 already do, and repeat strict-key checks for every nested v3 object. `JSONDecoder` alone does not establish a closed unknown-key policy. [VERIFIED: SiriusMac/Skins/SkinAppearance.swift:280-318] [CITED: https://github.com/swiftlang/swift/blob/main/stdlib/stdlib.docc/encoding-decoding-and-serialization.md]

### Pattern 2: Semantic registry has fixed source order; layout is visual only

**What:** Instantiate all current SwiftUI controls once in a stable source/VoiceOver/keyboard order, then use validated frames to position them in a `ZStack` or layout host. Decorations and drag overlays must be behind them, noninteractive, and accessibility-hidden. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:93-109] [VERIFIED: SiriusMac/Player/CompactPlayerView.swift:323-347]

**When to use:** Each v3 layout variant; retain the legacy stack renderer unchanged for v1/v2 where that minimizes compatibility risk. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:84-91]

### Pattern 3: Controller-owned atomic size transition

**What:** Give the window bridge the validated finite appearance policy, not raw manifest data. It computes the full NSWindow frame for the selected content size, chooses the appropriate visible screen, preserves top-left where valid, clamps once, applies matching `contentMinSize`/`contentMaxSize`, then persists the migrated position. [CITED: https://developer.apple.com/documentation/appkit/nswindow/framerect%28forcontentrect%3A%29] [CITED: https://developer.apple.com/documentation/appkit/nswindow/setframe%28_%3Adisplay%3A%29]

**When to use:** On initial attach, selection, render-time fallback, and restored selection. Native/legacy always resolve to the documented legacy size. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:111-116]

### Pattern 4: Drag overlay is app-owned and behind controls

**What:** Materialize only validated drag rectangles as clear SwiftUI overlays, `.accessibilityHidden(true)` and behind interactive slots, with `WindowDragGesture` plus `allowsWindowActivationEvents()`. [CITED: https://developer.apple.com/documentation/swiftui/windowdraggesture]

**When to use:** Only for v3 layouts after non-overlap and minimum-size validation. The UI contract fixes the minimum rectangle at `80 × 20pt`. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:107-109]

### Anti-Patterns to Avoid

- **Theme-specific renderer branches:** They let bundled themes bypass the public/import validator and make imported parity untestable. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-CONTEXT.md:20-23]
- **Raw frame values reaching `NSWindow`:** This turns package data into window policy; validate finite tokens and retain sizing exclusively in the controller. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-CONTEXT.md:33-36]
- **Visual reordering by changing SwiftUI source order:** It destabilizes VoiceOver and keyboard navigation; visual coordinates are the only theme-controlled aspect. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:93-99]
- **Treating an image frame as a hit-test frame:** The decoration must be behind semantic controls with hit testing disabled. [VERIFIED: SiriusMac/Player/CompactPlayerView.swift:339-347]
- **Persuading contrast/focus with skin colors alone:** Focus/state indicators remain app-owned and require validated clearance and readability. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:101-109]

## Common Pitfalls

### Pitfall 1: A v3 manifest validates but its asset accounting still decodes as v1

**What goes wrong:** The validator accepts up to six v3 asset fields, but `referencedAssetPaths` keeps decoding `SkinManifest` and only allows the old two asset paths. The importer then rejects legitimate v3 bundles as unexpected files—or worse, misses an unaccounted asset. [VERIFIED: SiriusMac/Skins/SkinPackageImporter.swift:514-520; SiriusMac/Skins/SkinPackageImporter.swift:552-560]

**How to avoid:** Define one v3 asset-reference accessor from the same strict raw-manifest branch used for validation, and use it for resolver, exact-file accounting, decode/type checks, digest, promotion revalidation, bundled lookup, and renderability checks.

### Pitfall 2: Geometry uses content coordinates but window fitting uses frame coordinates

**What goes wrong:** Applying a content-size delta directly to `window.frame` shifts a titled window or leaves part of the frame under system UI. AppKit distinguishes the content rectangle from the full frame. [CITED: https://developer.apple.com/documentation/appkit/nswindow/framerect%28forcontentrect%3A%29]

**How to avoid:** Derive a frame with `frameRect(forContentRect:)`, retain the visible top-left only when the complete frame fits, clamp against `NSScreen.visibleFrame`, then apply in one controller operation. [CITED: https://developer.apple.com/documentation/appkit/nswindow/setframe%28_%3Adisplay%3A%29]

### Pitfall 3: Drag overlay captures buttons or becomes a VoiceOver element

**What goes wrong:** A broad transparent drag layer is visually inert but steals pointer events or appears as an unnamed accessibility region.

**How to avoid:** Validate that drag rectangles do not overlap interactive frames, put them below controls, and set them accessibility-hidden. Apple’s example similarly places the drag overlay between content and controls. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:101-109] [CITED: https://developer.apple.com/documentation/swiftui/customizing-window-styles-and-state-restoration-behavior-in-macos]

### Pitfall 4: Decorations obscure state/focus or violate Reduce Motion

**What goes wrong:** A striking theme becomes unusable when the selected-state/focus ring is cropped, low contrast, or communicated only by parallax/bounce.

**How to avoid:** Validate the 4-point focus inset and app-owned indicator treatment; make the allowed crossfade optional under Reduce Motion and never use animation for state truth. Apple recommends reducing automatic/repetitive animation, including zooming, scaling, and peripheral movement, when Reduce Motion is active. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:101-120] [CITED: https://developer.apple.com/design/human-interface-guidelines/accessibility]

### Pitfall 5: Bundled art resembles the inspiration too closely

**What goes wrong:** “macOS 8”, “MiniDisc”, and “Frutiger Aero” become copied names, marks, icons, or recognizable proprietary art instead of inspiration.

**How to avoid:** Ship only the approved public names `Pixel Desk`, `Pocket Disc`, and `Aqua Vista`; retain per-asset provenance/source records and review names/artwork before bundling. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-CONTEXT.md:40-44]

## Code Examples

### Strict exact-key boundary

The existing manifest validator proves the appropriate boundary: it converts the raw JSON object to a dictionary, checks required/subset keys, then decodes only after that. Its exact closed-schema error case is `case unknownOrMissingKeys`. [VERIFIED: SiriusMac/Skins/SkinAppearance.swift:93-100; SiriusMac/Skins/SkinAppearance.swift:280-318]

```swift
// Reuse this pattern at every v3 object boundary; values remain manifest-defined.
let keys = Set(dictionary.keys)
guard requiredKeys.isSubset(of: keys), keys.isSubset(of: permittedKeys) else {
    throw SkinManifestValidationError.unknownOrMissingKeys
}
```

dragRegion
    .gesture(WindowDragGesture())
    .allowsWindowActivationEvents()
    .accessibilityHidden(true)

## Open Questions

1. **Exact transparent titlebar/traffic-light treatment**
   - What we know: The window must remain titled, key-capable, nonresizable, and visually silhouette-driven. [VERIFIED: .planning/phases/04.2-expressive-skin-architecture-bundled-themes/04.2-UI-SPEC.md:84-91]
   - What’s unclear: The most legible current-macOS balance of titlebar visibility, traffic-light placement, system shadow, and transparency cannot be established from static source alone.
   - Recommendation: Make this an early bounded AppKit proof task followed by the required authorized offline visual review; preserve Native as the rollback surface.

2. **v1/v2 implementation choice: direct renderer or deterministic migration**
