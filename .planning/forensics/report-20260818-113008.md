## Anomaly Review

### 1. False stall classification — HIGH

Both alerts violated the workflow's activity-based definition of a stall. Recent expected-branch commits existed inside the threshold in both cases. The common cause was monitoring total elapsed time/rough polling intervals without resetting the activity clock from the newest commit or executor status.

### 2. Genuine Xcode test-host linker defect — HIGH

Plan 01-07's focused XCTest invocation failed while linking `SiriusMacTests.xctest`, with undefined symbols including:

- `SiriusMac.WebAuthenticationBridge.useLoggedInSession()`
- `SiriusMac.WebAuthenticationBridge.removeAuthenticationResidue()`
- `SiriusXMClient.AuthenticationCredential.description.getter`

This is not evidence of executor inactivity. A fresh derived-data run reproduced the linker failure from the pre-existing `WebAuthenticationBridgeTests.o` before the new selected-composition test was in the generated Swift file list. A separate fresh app-target build passed, and the focused/full SwiftPM suites passed.

The project file provides a plausible configuration cause: the app target links the `SiriusXMClient` package product, but the `SiriusMacTests` target has an empty Frameworks phase and empty `packageProductDependencies`, relying only on `BUNDLE_LOADER`/`TEST_HOST`. Tests directly exercise app code whose signatures include package types. The exact repair should be verified in a dedicated test-target correction; it should not be guessed during plan close-out.

## Root Cause

The repeated user-facing failure was caused by a bug in how this orchestration session applied stall surveillance:

1. It treated approximately ten minutes since dispatch/waiting as the stall clock.
2. It did not recompute inactivity from the most recent expected-branch commit.
3. It escalated before sending a non-destructive status query to the executor.
4. Verification and close-out legitimately pushed total runtime past ten minutes even though activity gaps stayed below the threshold.

The Xcode linker failure is a second, independent issue: the unit-test target's package/app-host linkage is incomplete or inconsistent. It explains one failed verification command, but it did not cause either executor to stall.

## Recommendations

1. Track `last_activity` as the newest of: expected-branch commit time, summary modification time, or explicit executor progress/tool-boundary status. Reset the inactivity clock whenever it advances.
2. Require two consecutive inactive inspections and an explicit executor status query before presenting destructive recovery options.
3. Treat a running executor that reports close-out or verification progress as active even if no command is currently executing.
4. Diagnose and correct the `SiriusMacTests` linkage in a dedicated GSD debug/quick task, then run one clean focused XCTest after the configuration changes. Re-running the unchanged command is not useful.
5. Reconcile Plan 01-07's declared `files_modified` list with its recorded deviations so future scope checks distinguish expected integration edits from drift.
